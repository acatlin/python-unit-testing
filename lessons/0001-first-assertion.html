Your first assertion

You already test your code. You run a function, look at what comes back, and decide whether it seems right. This lesson turns that glance into one line of Python that can be run again tomorrow.

The check that disappears

Here is a small helper of the kind you write all the time while cleaning data. It rescales a numeric column so that its smallest value becomes 0 and its largest becomes 1. Type it into a Python console or a notebook cell.

That looks right, and you move on. The trouble is that the check lived only in your head. Next month you change rescale01(), or a classmate does, and nobody repeats it. A unit test is the same check written down as code, so the computer can repeat it for you after every change.

The Scientific Python Development Guide lists four ways this pays off: code you can trust to behave as expected; a living record of how the code is meant to behave, checked every time the test runs; protection against failure, from mistakes in your own code to changes in the packages you depend on; and the confidence to add features, fix bugs and reorganise code without breaking what already works.

Source: Scientific Python Development Guide, “Testing recommendations”, section “Advantages of Testing”.

Say what you expect

Python has a statement built for this: assert. It takes a condition. If the condition is true, nothing happens. If it is false, Python stops with an error. One assert statement is an assertion, and it is the building block of every test you will write.

Run it, and nothing is printed. Silence means the assertion passed. Read the line as a sentence: “I assert that rescale01() of 0, 5 and 10, as a list, equals [0, 0.5, 1].” The .tolist() turns the column into a plain Python list, so that == gives one answer for the whole thing. Lesson 3 shows what goes wrong without it.

Equal, or close enough?

Computers store most decimal numbers approximately, which leads to a famous surprise.

The same thing happens to your own functions. Rescaling 0.1, 0.2 and 0.3 should put the middle value at exactly one half.

An assertion that compared this with [0, 0.5, 1] using a bare == would fail for a reason that has nothing to do with a bug. The testing package pytest, which nearly everyone uses in Python, has the remedy. Install it once per environment. Type this in a terminal, which is your computer's command line and not the Python console with its >>> prompt; then go back to Python and import it.

Wrap the expected value in pytest.approx() and == ignores tiny floating-point differences (by default, anything smaller than one part in a million of the expected value).

“By default, approx considers numbers within a relative tolerance of 1e-6 (i.e. one part in a million) of its expected value to be equal.” pytest.approx() reference. Why decimals are approximate: Python tutorial, “Floating-Point Arithmetic”.

Use plain == for text, whole numbers and anything that must match exactly, and == pytest.approx(…) when the result is the outcome of arithmetic on decimals. Plain == is not fussy about one thing: it treats the whole number 1 and the decimal 1.0 as equal, which is why [0.0, 0.5, 1.0] == [0, 0.5, 1] is true.

Check yourself

Answer from memory, without scrolling up. Getting one wrong and reading why is worth more than getting it right by looking.

  1. You run an assert statement at the console and Python prints nothing at all. What happened?

    • The assertion passed without complaint.
    • The assertion was skipped entirely.
    • The assertion failed without output.
    • The assertion never actually ran.

    A passing assertion is silent. Only a failure prints anything: a traceback that ends in AssertionError.

  2. In assert rescale01(pd.Series([0, 5, 10])).tolist() == [0, 0.5, 1], what is on the right of ==?

    • The right answer, which you supplied yourself.
    • The value your function has actually returned.
    • The biggest numeric gap Python will allow.
    • The message printed when the check fails.

    The left side is the actual result (a call to your function). The right side is the expected result, which comes from you.

  3. Why does assert 0.1 + 0.2 == pytest.approx(0.3) pass even though 0.1 + 0.2 == 0.3 is False?

    • It ignores very tiny differences by default.
    • It rounds both values to two decimals.
    • It converts both values into character strings.
    • It only compares the types of values.

    pytest.approx() gives == a small numeric tolerance. A bare == has none, so it fails here.

  4. What does writing a check as an assertion give you that looking at console output does not?

    • It can be rerun after every change.
    • It makes the function run noticeably faster.
    • It removes any need for reading documentation.
    • It guarantees the function has no bugs.

    A written check is repeatable. It makes bugs less likely, not impossible: a test only covers the cases you thought to write.
