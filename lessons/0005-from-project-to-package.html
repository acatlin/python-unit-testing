From project to package

Your project already has a file of functions and a tests/ folder. That is most of a Python package. Taking the last step means Python can import your code from anywhere, the packages it depends on are written down, and pytest's settings live in one file.

By the end you can

Move your functions and tests into an installable package and run all of them with pytest.

From last time

  1. What does pytest.raises(TypeError, match="must be a numeric column") check about the error that is raised?

    • The error's type and its message.
    • The error's type and its traceback.
    • The function's result and its type.
    • The warning's type and its message.

    The first argument names the type of exception; match is a regular expression searched for in the error message.

  2. After finding a bug, why write the failing test before the fix?

    • It proves the test detects the bug.
    • It makes the fix run more quickly.
    • It hides the bug from other users.
    • It removes the need for a fix.

    A test you have seen fail is one you know is able to fail.

What changes, and what does not

Everything you learned about assertions and test functions carries over unchanged. Three chores go away.

ChorePlain projectPackage
Making your functions importableStart every run with python -m pytest, from the right folderInstall the package once; after that pytest on its own works
Recording what your code needsYou remember to install pandas and pytestTwo lists in the pyproject.toml file
Choosing pytest's settingsTyped on the command line each timeA table in the pyproject.toml file
The layout and the install step follow pytest, “Good Integration Practices”.

Build it

There are tools that generate a package for you, but a package is only three folders and a settings file, and building one by hand shows you what each part is for. Follow the steps.

  1. Make the folders. Create a new folder called cleaner that is not inside another project. Inside it, make src/cleaner/ and tests/. Copy your clean.py into src/cleaner/ and your test_clean.py into tests/. Then create an empty file called __init__.py next to clean.py; it marks the folder as a package that can be imported. 
    cleaner/
├── src/
│   └── cleaner/
│       ├── __init__.py
│       └── clean.py
└── tests/
    └── test_clean.py
  2. Write the settings file. Save this as pyproject.toml in the top cleaner folder.
  3. Make a virtual environment for the package and switch it on. Open a terminal in the top cleaner folder and run the two lines for your system, one at a time. Your prompt now starts with (.venv). If Windows PowerShell refuses to run the activate script, the Python documentation gives the one-time fix: Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser.
  4. Install your package into that environment, in editable mode (-e), together with the dev group. The dot means “the project in this folder”.
  5. Change one line in the test file. Your functions now live in the module clean inside the package cleaner, so the import says so.
  6. Run the tests. Plain pytest is enough now.
“You can then create a virtual environment and install your package in ‘editable’ mode, together with the dev group”; “pip install --group needs pip 25.1 or newer”. pytest, “Install package in a virtual environment”. If pip rejects --group, run python -m pip install --upgrade pip first. Creating and activating: Python Packaging User Guide; the PowerShell note: Python documentation, venv.

What you now have

cleaner/
├── pyproject.toml           settings: name, dependencies, pytest options
├── .venv/                   the virtual environment (never edit, never commit)
├── src/
│   └── cleaner/
│       ├── __init__.py      marks the folder as a package
│       └── clean.py         your functions
└── tests/
    └── test_clean.py        your tests

Compare this with the tree in Lesson 2. tests/ is exactly where it was. clean.py has moved down into src/cleaner/, and one file does the work that used to be yours.

pyproject.toml holds the package's settings in four tables.

TableWhat it says
[build-system]Which tool turns the folder into an installable package. You will not touch it again.
[project]The package's name and version, and dependencies: the packages your functions need. summarise_by() and its neighbours use pandas.
[dependency-groups]Packages that only the people working on the code need. pytest is used by your tests, not by your functions, so it goes in the dev group.
[tool.pytest]pytest's settings: look for tests in tests/, and import test files in the way pytest recommends for new projects.
“The [dependency-groups] table specifies dependencies for development tasks such as testing and linting.” Python Packaging User Guide, “Writing your pyproject.toml”. “For new projects, we recommend to use importlib import mode”. pytest, “Choosing a test layout”. The [tool.pytest] table needs pytest 9.

The editable install is what replaces python -m pytest. It tells the environment where your package's files are instead of copying them, so from cleaner.clean import … works from any folder, and every edit you make to clean.py takes effect the next time you run the tests. You install once, not after every change.

“Editable installs allow you to install your project without copying any files. Instead, the files in the development directory are added to Python's import path.” pip documentation, “Local project installs”.

The src/ folder looks like an extra layer, and it earns its place. With your code one level down, the tests can only reach it through the installed package, which is the way anyone else would use it.

“The src layout helps prevent accidental usage of the in-development copy of the code.” Python Packaging User Guide, “src layout vs flat layout”.
Common trap

If the run stops with ModuleNotFoundError: No module named 'cleaner', the package is not installed in the environment you are using. Either you skipped the install step, or you opened a new terminal: a virtual environment has to be activated again in every new terminal before pytest can see your package.

“If you open a new shell window and want to use the virtual environment, reactivate it.” Python Packaging User Guide, “Install packages in a virtual environment using pip and venv”.

The working loop

With a package, day-to-day work becomes a short cycle. You will repeat it many times an hour.

StepCommand
Edit a function or a testNothing to reload: the install is editable
Run every testpytest
Run only the tests whose names contain a wordpytest -k rescale01
Rerun only the tests that failed last timepytest --lf
Stop at the first failurepytest -x
-k: “Specifying which tests to run”. --lf: “Rerunning only failures or failures first”. -x: “Stopping after the first (or N) failures”.

Because running the tests is now one short word, you will run them far more often, and tests that are run often are the ones that catch things.

Try it

  1. Follow the six steps under “Build it” with your own project from Lesson 4. Finish with 12 passed or more. A finished copy is in examples/cleaner.
  2. Break clean_names() on purpose (delete .lower()), run pytest, and read the report. Run pytest --lf and notice how many tests it collects. Undo the change and run everything again.
  3. Add a new function to the package test-first: write a failing test, then make it pass. An idea: squish(), which trims a string and collapses runs of spaces into one. Put it in a new file, src/cleaner/text.py, with its tests in tests/test_text.py.

Check yourself

  1. In a package, what does the job that python -m pytest did in a plain project: letting the tests import your code?

    • An editable install of the package.
    • A second copy placed inside tests/.
    • A longer import line in __init__.py.
    • An extra option for python -m.

    python -m pip install -e . makes the package importable from any folder, so plain pytest can find it.

  2. Which command installs your package so that later edits to its code take effect without reinstalling?

    • pip install -e .
    • pip install --upgrade pip
    • pip install pandas pytest
    • pip install --group dev

    -e is short for editable, and the dot is the project in the current folder. Run it once per environment. Adding --group dev to that command installs pytest as well; on its own, --group dev installs pytest and not your package.

  3. Why can package tests say from cleaner.clean import … whichever folder you run them from?

    • The installed package is importable from anywhere.
    • Package tests never call your own functions.
    • Pytest copies your code into tests/ first.
    • Python searches every folder on the disk.

    Installing the package puts it on the import path of that environment, so the folder you happen to be in no longer matters.

  4. In pyproject.toml, where does pytest belong when only your tests need it?

    • Under [dependency-groups], in the dev group.
    • Under [project], in the dependencies list.
    • Under [build-system], in the requires list.
    • Under [tool.pytest], in the addopts list.

    dependencies is for what your functions need (pandas). Tools that only developers need, such as pytest, go in a dependency group.

  5. Which command reruns only the tests that failed on the previous run?

    • pytest --lf
    • pytest -x
    • pytest -k
    • pytest -v

    --lf stands for last failed. -x stops at the first failure, -k selects tests by name, and -v lists every test.

Where to go from here

You can now write, organise and run tests by hand, in a project or a package. There is more to learn, and later lessons in this course will take it up: parametrised tests that run one test over many inputs, fixtures and conftest.py for shared set-up, skipping tests, and measuring how much of your code the tests reach.

Testing is also a craft that people argue about. When you have a question with no clear answer in the documentation, such as how much testing is enough for an analysis project, ask people who do this for a living. The pytest project points to pytest discussions on GitHub “for general questions”.
