Edge cases, errors and bugs

Every test so far fed a function tidy input and checked a tidy answer. Real data is not tidy. This lesson is about the inputs that break things, and a habit that keeps a bug from coming back once you have fixed it.

Ask what could go wrong

The tests you have written cover the happy path: ordinary input, ordinary output. Bugs mostly live elsewhere. For a function that takes a column of data, run through this list and ask of each item, “what should happen?”

Deciding the answer is design work, and the test is where you record the decision. For missing values in rescale01(), a reasonable decision is “they stay missing, and the rest are rescaled as usual”:

This is a job for assert_series_equal(), not for .tolist() and ==. pandas stores a missing number as NaN, and NaN is not equal to anything, itself included, so a list containing one can never pass an == check. assert_series_equal() counts two missing values in the same position as a match.

np.nan == np.nan is False: pandas user guide, “Working with missing data”. The behaviour of assert_series_equal() with missing values was checked by running it.

The test passes already. That is a fine outcome: the behaviour is now written down, and a future edit that changes how missing values are handled will be caught.

A bug, caught test-first

Now the second item on the list. What does rescale01() do with a column where every value is the same?

The smallest and largest values are equal, so the function divides zero by zero. pandas does not raise an error for that; it returns NaN. One constant column would quietly fill a model matrix with missing values. That is a bug. The tempting move is to fix it straight away. Do this instead:

So, before actually writing any code, you should write your tests.
pandas contributing guide, “Test-driven development”

Step 1: write the test and watch it fail

Decide what should happen (all zeros is a sensible answer) and say so.

The failure matters. It proves that the test can see this bug. A test written after the fix passes the first time you run it, and you never find out whether it would have caught anything.

“Check that your test fails when it should!” Scientific Python Development Guide, “Testing recommendations”.

Step 2: fix the function

Step 3: run everything again

Run all the tests, not just the new one. The new test should pass, and so should every old one. The old ones are how you know the fix did not break something else.

This fail-first rhythm is often called “red, green”. The pandas guide describes it as writing “an (initially failing) automated test case” and then “the minimum amount of code to pass that test”.

Expecting an error

For the wrong type, the right behaviour is to stop with a clear message. pytest.raises() wraps a block of code. The test passes when the block raises the kind of error you named and fails when it does not.

Common trap

That also passes. NameError: name 'rescale1' is not defined is an error, and Exception is the family that nearly every Python error belongs to, so pytest.raises(Exception) is satisfied by any error at all. A test like this can stay green for years while testing nothing.

“Because Exception is the base class of almost all exceptions, it is easy for this to hide real bugs”. pytest.raises() reference.

Say which error you mean, in two ways. Name the specific type of exception, and give match a piece of text (a regular expression) that the error message must contain. pytest.raises() belongs to pytest, so add import pytest to the imports at the top of the test file first.

match: “a string containing a regular expression… that is tested against the string representation of the exception”. pytest, “Matching exception messages”.

Warnings

parse_money(pd.Series(["n/a"])) returns a missing value and warns 1 value(s) could not be parsed as money. If that is the behaviour you want, say so with pytest.warns(), which works like pytest.raises(). To state that well-formed input is quiet, turn warnings into errors for the length of the test, so that any warning fails it. That uses Python's own warnings module, which needs importing too. A warning that no test asked for does not fail the test, but it is not hidden either. pytest lists it under a warnings summary heading and counts it on the last line of the report:

Treat a warning count on the last line as something to investigate.

One behaviour per test

Your test file now has several short tests for rescale01() rather than one long one. Keep it that way. When the constant-column test fails, its name tells you what broke before you read a line of code, and because a test stops at its first failing assertion, short tests hide less.

“Test one thing at a time: A single test should test a single behavior, and it is better to write many test cases for a single function or class, than one giant case.” Scientific Python Development Guide.

Give every test a name of its own. If two functions in one file share a name, Python keeps only the second, and pytest never sees the first.

Check yourself

  1. A test wraps rescale1(pd.Series(["a"])) in with pytest.raises(Exception):, where the function name is a typo. What happens when it runs?

    • It passes, since any error satisfies it.
    • It fails, since the function is missing.
    • It is skipped, since nothing was called.
    • It warns, since the name looks wrong.

    NameError is itself an exception, and pytest.raises(Exception) accepts any exception.

  2. How do you make sure pytest.raises() saw the error you intended?

    • Give the exception type and a match.
    • Wrap the block inside another test function.
    • Call the function twice inside the block.
    • Put a plain assert around the call.

    Name the specific type and add a pattern for the message, as in pytest.raises(TypeError, match="must be a numeric column").

  3. You discover that rescale01(pd.Series([5, 5, 5])) returns NaN. What is the best first move?

    • Write a new test that reproduces it.
    • Fix the function before you forget how.
    • Delete the tests that still pass now.
    • Note it in a comment for later.

    A test that fails first proves it can detect the bug, and stays behind to stop the bug returning.

  4. Which set of inputs covers the usual edge cases for a numeric helper?

    • Missing values, identical values, and wrong types.
    • Three ordinary numeric columns of different lengths.
    • The same typical column, run three times.
    • Whatever values appeared in the last dataset.

    Edge cases sit at the boundaries of what the function was written for. More ordinary input mostly re-tests the happy path.

  5. A test calls parse_money(pd.Series(["n/a"])) without using pytest.warns(). What does the run report?

    • A pass, plus one warning in the summary.
    • A failure, with the warning as the reason.
    • A skip, with the warning as the reason.
    • A pass, with no mention of the warning.

    Unexpected warnings are listed and counted (1 warning on the last line), but they do not make the test fail.
