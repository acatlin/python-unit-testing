Choosing the right assertion

So far every check has been assert … == …. For lists, text and single numbers that is all you need. For the columns and data frames that fill data science work, it is the wrong tool. This lesson gives you the dozen forms you need, and shows why the specific one gets you a failure message that tells you what went wrong.

  2. Which ordering runs from the smallest unit to the largest?

    • Assertion, test, file.
    • Test, assertion, file.
    • File, test, assertion.
    • Assertion, file, test.

    Assertions are grouped into tests, and tests are organised in files.

Why not == for everything?

In Lesson 1 you compared a column with a list by calling .tolist() first. Here is what happens if you compare two columns directly. The expected value is wrong on purpose, so the check ought to fail.

That is not a failed assertion; it is a crash. On two Series, == compares element by element and returns a whole column of True and False. assert needs a single answer, and pandas refuses to guess one. There are two ways round it. Compare what each tells you when the check fails.

“pandas follows the NumPy convention of raising an error when you try to convert something to a bool.” pandas user guide, “Frequently Asked Questions”.

The first says only that something was False, and leaves you to pick through two columns squashed onto one line each. The second tells you that one value in three differs, that it is the one at position 2, and that the function returned 1.0 where you said 2.0. That is what you need to start fixing it. pandas ships these functions for exactly this purpose: assert_series_equal() for one column and assert_frame_equal() for a whole data frame.

assert_frame_equal() “is intended to compare two DataFrames and output any differences. It is mostly intended for use in unit tests.” pandas API reference.

Every row except two is a plain assert, and that is deliberate. Because pytest shows you the values on both sides of a failed assert, an ordinary Python expression is usually the most specific check there is. assert len(x) == 4 fails with assert 3 == 4, which tells you the real length. The two pandas functions exist because whole columns and data frames are the one place where == lets you down.

Testing a function that returns a data frame

Most of your functions take a data frame and return one. Here is a small pandas wrapper from clean.py that counts rows and averages a column within groups.

The recipe has three parts, and it works for nearly any data-frame function. Arrange a tiny input by hand. Act by calling the function. Assert by comparing with an expected result that you also typed by hand.

“You can think of a test as being broken down into four steps”: Arrange, Act, Assert and Cleanup. pytest, “Anatomy of a test”. These tests leave nothing behind, so they need no cleanup.

Three rows are enough. You can check the answer in your head (two people in “a” averaging 15, one in “b” at 60), and if the test fails the difference is small enough to read. The result goes first and the expected frame second, so in the report [left] is what the function returned and [right] is what you said. Had you typed the mean for “b” as 50, the report would say:

pandas points at the column (mean) and the row (position 1, counting from 0) that disagree, which is why it pays to compare whole data frames with assert_frame_equal() when they are small.

Notice that the expected means are typed as 15.0 and 60.0, not 15 and 60. assert_frame_equal() is forgiving about floating-point noise and strict about types: an average is a column of decimals (float64), and a column of whole numbers (int64) does not count as equal to it. The second “Try it” step lets you see that for yourself.

check_dtype: “Whether to check the DataFrame dtype is identical”, default True. rtol: “Relative tolerance”, default 1e-5. pandas API reference.
Common trap

Never build the expected value by calling the function you are testing. assert_frame_equal(summarise_by(staff, "dept", "pay"), summarise_by(staff, "dept", "pay")) passes no matter how broken the function is. The expected side must come from somewhere else: your own arithmetic.

Structure checks

Sometimes you care less about exact values and more about the shape of the result: it is a data frame, and it has the documented columns. Those get a test of their own.

“Unit tests should be simple, isolated, and run very quickly.” Scientific Python Development Guide, “Testing recommendations”.

Check yourself

  1. Why prefer pd.testing.assert_series_equal(result, expected) to assert result.equals(expected)?

    • Its failure message shows which values differ.
    • It runs quicker on extremely long columns.
    • It is the single form pytest accepts.
    • It also checks the function's running time.

    Both work. The pandas function tells you which position differs and what the two values were; .equals() can only say False.

  2. A function returns a column of decimals (float64). Your hand-typed expected frame has whole numbers, [15, 60], in that column. What does assert_frame_equal() do by default?

    • Fails, because the two dtypes differ.
    • Passes, because the values are equal.
    • Fails, because decimals cannot be compared.
    • Passes, because dtypes are never checked.

    By default the dtypes must be identical, and the report says Attribute "dtype" are different, with float64 on the left and int64 on the right. Type the decimals, or pass check_dtype=False to compare values only.

  3. You want to check that a result has exactly the columns dept, n and mean, in that order. Which check is the most direct?

    • Compare list(out.columns) with a typed list.
    • Compare len(out.columns) with the number three.
    • Compare out.dtypes with a typed list.
    • Compare out.shape with a typed tuple.

    assert list(out.columns) == ["dept", "n", "mean"]. The length or the shape would confirm there are three columns but not which ones.

  4. What does assert rescale01(pd.Series([1, 2, 3])).dtype == "int64" do?

    • Fails, because division returns a float.
    • Passes, because the input was integer.
    • Fails, because dtypes cannot be tested.
    • Passes, because floats count as integers.

    rescale01() divides, and / in pandas always gives decimals. The report begins assert dtype('float64') == 'int64'.

  5. Where should the expected value in a summarise_by() test come from?

    • A small expected frame typed by hand.
    • One more call to the same function.
    • A random sample of the production data.
    • The full dataset with thousands of rows.

    The expected value has to be independent of the code under test and small enough to verify by eye.
